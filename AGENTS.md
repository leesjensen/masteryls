## What MasteryLS is

MasteryLS is a web-based **learning management / mastery-learning platform**. Instructors author courses as Markdown (stored in GitHub), learners work through topics containing interactive **interactions** (multiple-choice, essays, AI-graded prompts, file/URL submissions, disciplinary-reasoning assessments, interviews, attendance, etc.), and progress/mastery is tracked per enrollment. It integrates with **Canvas** (gradebook, Due date delta, attendance) and uses the **Google Gemini** API for AI features (feedback, grading, content generation).

Public site: `masteryls.com`. User-facing docs live in `docs/` (see that folder; the in-app **About** page renders the repo README + linked docs by fetching them from GitHub raw `main` at runtime).

## Tech stack

- **Frontend:** React 19 + React Router 7, Vite 7, Tailwind CSS 4, Monaco (editor), TipTap, lucide-react, react-markdown (+ remark/rehype plugins), Chart.js. PWA via `vite-plugin-pwa`.
- **Backend:** **Supabase** (Postgres + Auth + Storage + Edge Functions). No custom server — the client talks to Supabase directly plus a set of Deno **edge functions** for privileged/aggregated operations.
- **AI:** Google Gemini (via the `gemini` edge function and `src/ai/aiContentGenerator.js`). Model ids are defined in a few places — see `install/supabase/functions/gemini/index.ts` (`defaultModel`), `install/supabase/functions/githubgrade/handler.js`, and `src/service/service.ts` (image model).
- **Course content:** authored in Markdown and loaded from **GitHub** repositories at runtime (`src/course.js`, `Course.load`).
- **Tests:** Playwright (e2e, in `tests/`) and `node:test` unit tests (co-located `*.test.js` under `src/` and `install/supabase/functions/`).

## Architecture & conventions

- **Layering:** UI (`views`/`components`) → `useCourseOperations` (operations API) → `service.ts` (Supabase/edge/GitHub) → Supabase. Prefer adding logic to `useCourseOperations`/`service` rather than calling Supabase from components.
- **Edge functions** handle privileged reads/writes and server-side aggregation. Each is split into a **pure `handler.js`** (unit-tested with a mock Supabase client) and a thin **`index.ts`** that wires Deno + the real client. Add tests to the handler, not the wiring. Examples: `masteryoverview` (course roster), `canvasgradebook`, `githubgrade` (AI grading), `gemini`, `progressrecord`.
- **Permissions** come from `model.ts`: `isRoot()`, `isEditor(courseId)`, `isMentor(courseId)`, `canOverseeCourse(courseId)` (root OR editor OR mentor). "Overseer" = can view/manage a course's learners.
- **Interactions** are authored as fenced ```masteryls code blocks inside topic Markdown; `src/components/instruction/`parses and renders them by`type`.
- **TOC in-topic headings.** The TOC lists the currently-viewed topic's level-2 (`##`) headings indented under it (auto-expanded, static jump list) so a learner can jump within the topic. `src/contents.jsx` fetches the current topic's markdown (via `courseOps.getTopic`, which caches in `course.markdownCache`) and parses it with `src/utils/topicHeadings.js` (`parseTopicHeadings` → `[{ text, slug }]`, ATX `##` only, skips fenced/`masteryls` code blocks); `TopicItem` renders the jump-list as `#slug` anchors routed through `handleSidebarLinkClick`. The `#slug` matches the heading's DOM id because both the TOC and `Markdown.jsx` build it from the shared `src/utils/headingSlug.js` — keep using that helper so anchors and ids never drift.
- **In-app navigation links** share `src/utils/linkNavigation.js` so they behave consistently and render as real `<a href>` anchors (which is what lets the browser offer "Open in new tab/window" on a right/modifier-click). `handleInAppLinkClick` intercepts a plain primary click to navigate inside the SPA and lets a modifier-click fall through to the browser. TOC sidebar links (topics, schedule, attendance) use `handleSidebarLinkClick`, which additionally collapses the sidebar (mobile viewport, or pinned-open `'end'`) before navigating. The classroom toolbar icons (`toolbar.jsx` `ToolBarButton`/`MasteryPie`) take an `href` and render as anchors too — in-app ones via `handleInAppLinkClick`, `external` ones (Canvas, GitHub) as `target="_blank"`. Add new links via these helpers rather than a bare `<button onClick={navigate}>`, so right-click-to-open and plain-click navigation stay uniform.
- **Shared UI primitives / design system.** Common form and dialog chrome lives in `src/components/ui/` — `Button`, `Input`, `Textarea`, `Select`, and `Modal` (a `<dialog>` shell), all composing their Tailwind classes from `src/components/ui/styles.js`, the single source of truth for radius, border, focus ring, disabled state, button variants (`primary|secondary|outline|danger|ghost`) and sizes (`xs|sm|md`); `styles.js` is unit-tested in `styles.test.js`. Build chrome from these primitives rather than re-deriving raw classes. The accent/signifier colour is **blue**; amber is reserved for semantic uses only (the AI "Discuss" button, the exam/DRA-final/interview-final assessment theme, warnings/banners, data-viz, and categorical colour arrays). Native `window.confirm`/`window.prompt`/`alert()` are **not used**: the app-wide `AlertProvider` (`src/contexts/AlertContext.jsx`, mounted in `index.jsx`) exposes `useAlert()` → `showAlert({message,type})`, `showConfirm(options) → Promise<boolean>`, and `showPrompt(options) → Promise<string|null>`, all rendered with the `Modal`/`Button`/`Input` primitives (`options` may be a message string or `{ message, title, confirmButtonText, cancelButtonText, danger, placeholder, initialValue }`). They are named `show*` (not `confirm`/`prompt`) deliberately, so a consumer can never shadow the `window.confirm`/`window.prompt` globals and silently fall back to a native dialog. The ref-driven dialog helpers `hooks/confirmDialog.jsx` and `hooks/inputDialog.jsx` also wrap `Modal`. **Tabs** are one component (`src/components/Tabs.jsx`): `variant="fill"` for equal-width tab bars (sidebar, discussion panel), `variant="scroll"` for content-width scrollable tabs (assessment workspaces) — there is no separate `TabBar`.
- **Markdown rendering & styling.** Topic prose is styled by a self-contained, token-based `src/components/markdown.css` (`--md-*` tokens for color/elevation/tables/etc.); `github-markdown-css` was removed. Dark mode re-points those tokens in `src/dark.css` (keep the two in sync when adding a token). `Markdown.jsx` is the live renderer and `MarkdownStatic.jsx` the static/export one. `MarkdownInstruction` caps normal topics to a centered `max-w` reading column but renders **schedule** topics full-width with a locked (sticky) header row — schedule tables carry the `markdown-table-scroll--sticky-head` wrapper, whose styles live in `markdown.css`.
- **Single source of truth for derived metrics.** Mastery/time/completion are derived from the enrollment's progress blob by **`src/utils/progressSummary.js` (`deriveProgressSummary`)** — on the client, which has the course structure. Do **not** add a second implementation (e.g., server-side) that can drift; that drift was a real bug. If the server must restrict data, do it on stable columns (e.g., `enrollment.createdAt`), not on recomputed values.

## Data model essentials (gotchas)

- **`enrollment.progress` is a cached JSON rollup**, not the source of truth for history. It can be stale (mastery was intentionally moved to runtime derivation to avoid a write race). The **`progress` table is an append-only event log** — every attempt/action is its own row with `createdAt` and `details`. "First attempt vs latest attempt" summaries read the full `progress` history.
- **Terms, Schedules, and Sections** (course-scoped DB tables: `term`, `schedule`, `section`). A **term** is a period of instruction (semester/quarter/short block); a **schedule** is the content/delivery calendar whose Markdown content stays in GitHub at `schedule.contentPath` (the DB row is metadata); a **section** ties a roster to one schedule within a term (a schedule may back many sections). Each **`enrollment.sectionId`** (nullable) locks a learner to one section → one schedule. Schedule resolution is **section-derived** via `src/utils/scheduleResolution.js` (`resolveLearnerSchedule`): `getScheduleFiles`/`getScheduleTopic`/`getLockedScheduleFileId` (in `useCourseOperations.jsx`) build descriptors from the **DB `course.schedules`** rows (by `contentPath`, descriptor id = schedule id) when present, falling back to the legacy GitHub `course.json` `schedule.files` (descriptor id = file id) / `enrollment.settings.selectedScheduleFile` when there are no DB schedule rows (schedule-less or not-yet-migrated courses). A learner sees only their section's schedule (picker hidden/locked); overseers keep the full picker, except when **observing** a learner (they then see that learner's locked schedule). Sections/schedules are loaded in `getCourse` (`useCourseOperations.jsx`) and attached as `course.sections`/`course.schedules`; the newer Terms & Sections flow uses DB rows, while the legacy schedule creation/editor path can still read and write `course.json` schedule data when no DB schedule rows exist. Existing enrollments were migrated to sections by a one-time backfill (built from each course's legacy `course.json` schedule files, keyed on `schedule.legacyFileId`, setting `enrollment.sectionId` only when null); that migration is complete and its script/helper have been removed. `term`/`schedule`/`section` are publicly readable; writes are root/editor (`auth_manages_course`). Editors/mentors remain **course-scoped** (no section-scoped permissions). At enrollment, `service.createEnrollment` auto-assigns the sole section when a course has exactly one; when a course has **multiple** sections the dashboard self-enroll shows a **section picker** (`dashboardView.jsx`) and passes the chosen `sectionId`. The picker offers only sections whose schedule's date range includes today (`src/utils/sectionEnrollment.js` `enrollableSections`); a section with no schedule or an undated schedule is always offered, and a course whose sections are all outside their schedule date ranges shows a "no open sections" message. Editors manage **terms** and **sections** in the **Terms & Sections view** (`src/views/sectionsAdmin/sectionsAdminView.jsx`), which renders **in the classroom content pane** as a synthetic `sections` topic (`courseOps.getSectionsTopic`, editor/root only — learners never see it) so it reads as part of the course rather than a separate screen. It is reached from the course **TOC** entry (`contents.jsx`, alongside Schedule/Attendance), which routes to `course/:courseId/sections`; `ClassroomPage` resolves the route like the schedule/attendance routes without persisting it as the landing topic. The classroom owns the app bar (course title + the topic title "Terms & Sections"), so the view no longer sets it itself. Sections are shown nested under their term, so a section's term is conveyed by its grouping, not a per-row dropdown; adding uses distinct highlighted forms. CRUD via `service` `createTerm`/`updateTerm`/`createSection`/`updateSection`/`setEnrollmentSection`. **Deletion** (`service.deleteSection`/`deleteTerm`, gated in the UI, never for items with learners): a section shows trash only when it has **0 learners and is not the last section in its term** (a term always keeps ≥1 section); a term shows **"Delete term"** only when none of its sections have learners, which removes the term and its sections (`section.termId` cascades) but **keeps its schedules** — `deleteTerm` first detaches them (`schedule.termId → null`) so the `schedule.termId` cascade does not drop them, since schedules are managed independently and may back sections in other terms. The same view lists schedules below terms with matching card formatting, and supports renaming, editing their date range (`service.updateScheduleRow`), **copying** a schedule, **viewing** one (a View button that sets `selectedScheduleFile` via `saveEnrollmentUiSettings` and navigates to the classroom `…/schedule` route), and creating a new one — `createCourseSchedule`/`copyCourseSchedule` (`useCourseOperations.jsx`) commit the markdown to GitHub and insert a DB `schedule` row with its `contentPath`, so brand-new schedules resolve natively (no `course.json` write). A schedule's **title and date range are owned here (the DB row)**: the classroom **schedule editor** (`src/components/editor/scheduleEditor.jsx`) edits only the schedule *content* (weeks/sessions, external links, special days) — it no longer has a title field or a "Dates covered" range. The **schedule name is not stored in the markdown**: `serializeScheduleMarkdown` does not write a `# ` title heading, and the displayed name comes from the DB `schedule.title`. `parseScheduleMarkdown` still skips a leading `# ` heading so legacy content authored with one parses cleanly. Legacy schedule file metadata is retained during fallback compatibility; learner section assignment lives in MasteryView/cohorts and editor bulk add-learner workflows.
- **MasteryView roster** (`src/views/masteryView/`) fetches a _trimmed_ per-enrollment blob from the `masteryoverview` edge function and does **sorting, filtering, and pagination entirely client-side** (so display and ordering always share one computation path). A single-learner drill-down request returns the _full_ blob. The **Section** filter restricts the roster server-side by `enrollment.sectionId` (the `masteryoverview` edge function accepts an optional `sectionId`); "All sections" fetches the whole course. (A legacy `startDate`/`endDate` `enrollment.createdAt` window is still honored by the edge function for backward compatibility, but the UI now filters by section.) When attendance is enabled for the course, the roster requests `includeAttendance: true`; the edge function then counts each learner's type-`attendance` progress rows (`tallyAttendanceByLearner`) and returns `attendedCount` per row, which the table shows as a sortable **"Classes Attended"** column (raw attended count, no total — a course can span multiple sections). The field is omitted when not requested, so non-attendance courses pay no extra query. On the single-learner drill-down (`learnerMasteryView.jsx`), when the viewer is an overseer and the course is Canvas-linked (`course.externalRefs.canvasCourseId`), a **"Canvas grades"** link appears to that learner's Canvas grades page. Canvas's web route needs the learner's numeric Canvas user id, which isn't stored in MasteryLS — it's resolved on demand by the `canvasgradebook` edge function's `mode: 'userLookup'` (matching by email/login via `findCanvasLearner`), and the URL is built by `getCanvasGradesUrl` in `canvasSync.js`. `userLookup` is a read-only overseer action so it also admits mentors; grade submission stays root/editor/self. The drill-down's chart panel (alongside Last Interaction / Daily Activity / Attendance) also offers a **Canvas** tab when that link resolves; opening it lazy-loads the learner's current Canvas grades via the `canvasgradebook` `mode: 'grades'` (overall course grade + per-assignment breakdown, trimmed by `buildGradeSummary`; read-only, overseer-or-self, mentors included) and renders them with `canvasGradesPanel.jsx`.
- **Attendance is section-based.** It uses a dedicated `attendance` table (each session carries a `sectionId`) + Postgres **RPCs** (`open_attendance(catalogId, sectionId, questions)`, `close_attendance`, `record_attendance`, `attendance_sessions(catalogId, sectionId?)`) under RLS; a check-in writes a `progress` row of type `attendance` referencing the session, with the learner's answers in `details.answers` keyed by question id. Attendance is **enabled per section** via `section.attendanceEnabled` (the old course-level `course.settings.attendance` flag was removed); editors/root manage this setting in the Terms & Sections view (`sectionsAdminView.jsx`), while the attendance view lets them open sessions for enabled sections (`attendanceAdmin.jsx`). The attendance affordance is shown to a learner only when their section has attendance enabled (`getAttendanceTopic`/`courseHasAttendance` in `useCourseOperations.jsx`). At most one session may be open per section. Opening attendance picks a section; `attendance_sessions` scopes sessions and the `enrolledCount` denominator to a section when given one. Every session asks the standard wellness question (`DEFAULT_ATTENDANCE_QUESTION`, id `q1`, in `attendanceUtils.js`); `attendance_sessions` returns a per-session `answerTally` (`{ [questionId]: { [choice]: count } }`) so the charts can show the results. There are two attendance charts, named as siblings and sharing `BarChartSvg`, `attendanceUtils.js`, and the `SentimentLegend` swatch row (`sentimentLegend.jsx`): **`courseAttendanceChart.jsx`** (`CourseAttendanceChart`) stacks every session's answers as sentiment-coloured bars for the whole course (instructor Attendance page + MasteryView course overview); **`learnerAttendanceChart.jsx`** (`LearnerAttendanceChart`) draws only the classes one learner attended, each bar coloured by their answer (learner's own Attendance page + MasteryView learner drill-down). Now that attendance is section-based, passing the learner's `sectionId` scopes the sessions so the chart shows an honest **"attended N of M"** (M = that section's sessions); without a `sectionId` it falls back to the attended-only view (no total). The learner's own page threads `courseOps.getCurrentSectionId()`; the MasteryView drill-down does not yet pass a section (shows attended-only there for now). Sentiment colours/segment helpers live in `attendanceUtils.js`; handle legacy sessions/rows that predate the question (no answer → neutral "No response"). **Historical sessions** created before section-based attendance carry `sectionId = null`; a one-time backfill (since removed) attributed them to a section **only for single-section courses** (closed sessions), leaving 0-/multi-section courses' sessions null for manual handling — so a null `sectionId` remains a valid "unattributed legacy" state the charts/RPCs still handle.
- **Course content** is not in the DB — it's Markdown pulled from GitHub. The `topic` table is only a full-text search index.

## Testing

Commands (see `package.json`):

- `npm run test:unit` — node unit tests (`src/**/*.test.js`), pure logic.
- `npm run test:edge-auth` — edge-function handler tests (`install/supabase/functions/**`).
- `npm test` — Playwright e2e (`tests/`). Needs the dev server/browsers; specs mock Supabase/GitHub via route interception (`tests/testInit`, `tests/fixtures`).
- `npm run build` — `vite build`; use it as an integration smoke check for client changes.

**Expected workflow (not optional):**

- While developing a feature, **run the tests relevant to what you're touching** (the unit/handler test for the logic, the matching Playwright spec for the UI) and keep them green as you go.
- On **completion of a feature, run the full suite** (`test:unit`, `test:edge-auth`, and the Playwright specs, plus `vite build`) before considering it done.
- **New features and bug fixes should add/adjust tests** that raise confidence and guard against regression. Edge-function logic → handler test; pure helpers → `*.test.js`; user-facing behavior → Playwright spec. When a fix is prompted by a bug, add the test that would have caught it.

## Deployment notes

- **Edge functions must be deployed** to take effect (they run on the hosted Supabase project, not from the local tree): `supabase functions deploy <name> --project-ref <ref>`. Changing a `handler.js` without deploying does nothing in production.
- **Schema changes** (`install/supabase/schema.sql`) — tables/indexes/RLS/RPCs — must be applied to the database separately.
- **Client/server contract changes ship together.** If an edge function's request/response shape changes, deploy it with the client release that depends on it; there is no backward-compat window unless you build one.
- The in-app **About page reads docs from GitHub `main` at runtime**, so doc/README path changes only take effect once merged to `main`, and relative image paths in a doc resolve relative to that doc's location in the repo.

## Working principles (how to make changes here)

- **Good design & patterns.** Favor clear, well-factored solutions over quick hacks. Respect the existing layering (UI → operations hook → service → Supabase) and the pure-handler/thin-wiring split for edge functions.
- **Modularity & clear organization.** Keep responsibilities separated; put pure logic in `utils/` (testable) and keep components focused. Reuse existing helpers (e.g., `deriveProgressSummary`, `scheduleMarkdown`) instead of re-implementing. Avoid duplicated computation paths that can drift.
- **Testing raises confidence.** Treat coverage as a feature: add tests that make new behavior safe to change and catch regressions. Run relevant tests during development and the full suite at feature completion (see Testing).
- **Suggest alternatives.** Don't just execute the literal request — when a cleaner design, a better-scaling approach, or a simpler path exists, surface it (with a recommendation) before or alongside doing the work. Flag tradeoffs the requester may not have considered.
- **Backward compatibility.** When changing existing code, data shapes, APIs, edge-function contracts, or the DB schema, consider existing data and callers. Prefer additive/compatible changes; when a breaking change is warranted, say so explicitly and coordinate the pieces (client + edge function + schema) that must change together.
- **Keep this file updated.** Reflect any architectural, data-model, workflow, feature, or layout change here as part of the same change.
- **Keep user documentation current.** For every code change, review the relevant documentation under `docs/` and update it in the same change whenever behavior, workflows, settings, or other documented details have changed. Treat stale user-facing documentation as unfinished work.
