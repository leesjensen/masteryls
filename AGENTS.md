## What MasteryLS is

MasteryLS is a web-based **learning management / mastery-learning platform**. Instructors author courses as Markdown (stored in GitHub), learners work through topics containing interactive **interactions** (multiple-choice, essays, AI-graded prompts, file/URL submissions, disciplinary-reasoning assessments, interviews, attendance, etc.), and progress/mastery is tracked per enrollment. It integrates with **Canvas** (gradebook, Due date delta, attendance) and uses the **Google Gemini** API for AI features (feedback, grading, content generation).

Public site: `masteryls.com`. User-facing docs live in `docs/` (see that folder; the in-app **About** page renders the repo README + linked docs by fetching them from GitHub raw `main` at runtime).

## Tech stack

- **Frontend:** React 19 + React Router 7, Vite 7, Tailwind CSS 4, Monaco (editor), TipTap, lucide-react, react-markdown (+ remark/rehype plugins), Chart.js. PWA via `vite-plugin-pwa`.
- **Backend:** **Supabase** (Postgres + Auth + Storage + Edge Functions). No custom server — the client talks to Supabase directly plus a set of Deno **edge functions** for privileged/aggregated operations.
- **AI:** Google Gemini (via the `gemini` edge function and `src/ai/aiContentGenerator.js`). Model ids are defined in a few places — see `install/supabase/functions/gemini/index.ts` (`defaultModel`), `install/supabase/functions/githubgrade/handler.js`, and `src/service/service.ts` (image model).
- **Course content:** authored in Markdown and loaded from **GitHub** repositories at runtime (`src/course.js`, `Course.load`).
- **Tests:** Playwright (e2e, in `tests/`) and `node:test` unit tests (co-located `*.test.js` under `src/` and `install/supabase/functions/`).

## Architecture & conventions

- **Layering:** UI (`views`/`components`) → `useCourseOperations` (operations API) → `service.ts` (Supabase/edge/GitHub) → Supabase. Prefer adding logic to `useCourseOperations`/`service` rather than calling Supabase from components.
- **Edge functions** handle privileged reads/writes and server-side aggregation. Each is split into a **pure `handler.js`** (unit-tested with a mock Supabase client) and a thin **`index.ts`** that wires Deno + the real client. Add tests to the handler, not the wiring. Examples: `masteryoverview` (course roster), `canvasgradebook`, `githubgrade` (AI grading), `gemini`, `progressrecord`.
- **Permissions** come from `model.ts`: `isRoot()`, `isEditor(courseId)`, `isMentor(courseId)`, `canOverseeCourse(courseId)` (root OR editor OR mentor). "Overseer" = can view/manage a course's learners.
- **Interactions** are authored as fenced ```masteryls code blocks inside topic Markdown; `src/components/instruction/`parses and renders them by`type`.
- **TOC in-topic headings.** The TOC lists the currently-viewed topic's level-2 (`##`) headings indented under it (auto-expanded, static jump list) so a learner can jump within the topic. `src/contents.jsx` fetches the current topic's markdown (via `courseOps.getTopic`, which caches in `course.markdownCache`) and parses it with `src/utils/topicHeadings.js` (`parseTopicHeadings` → `[{ text, slug }]`, ATX `##` only, skips fenced/`masteryls` code blocks); `TopicItem` renders the jump-list as `#slug` anchors routed through `handleSidebarLinkClick`. The `#slug` matches the heading's DOM id because both the TOC and `Markdown.jsx` build it from the shared `src/utils/headingSlug.js` — keep using that helper so anchors and ids never drift.
- **In-app navigation links** share `src/utils/linkNavigation.js` so they behave consistently and render as real `<a href>` anchors (which is what lets the browser offer "Open in new tab/window" on a right/modifier-click). `handleInAppLinkClick` intercepts a plain primary click to navigate inside the SPA and lets a modifier-click fall through to the browser. TOC sidebar links (topics, schedule, attendance) use `handleSidebarLinkClick`, which additionally collapses the sidebar (mobile viewport, or pinned-open `'end'`) before navigating. The classroom toolbar icons (`toolbar.jsx` `ToolBarButton`/`MasteryPie`) take an `href` and render as anchors too — in-app ones via `handleInAppLinkClick`, `external` ones (Canvas, GitHub) as `target="_blank"`. Add new links via these helpers rather than a bare `<button onClick={navigate}>`, so right-click-to-open and plain-click navigation stay uniform.
- **GitHub content reads vs. edits (stale-overwrite protection).** Topic/schedule **reads** are pinned to a per-session commit snapshot (`src/utils/githubRawSnapshot.js` caches `main`→SHA in a module-level `snapshotCache`, advanced only when this session commits) so a learner's reads stay consistent and CDN-cacheable. **Editing is different:** entering edit mode loads the **latest HEAD** via the Contents API (`service.getGitHubFileAtHead` → `courseOps.getTopicForEdit` / `getScheduleTopicContentForEdit`), bypassing the snapshot, and remembers the file's **blob sha**. Commits are **optimistic-concurrency guarded**: `service.updateGitHubFile(url, content, token, msg, baseSha)` PUTs with that base sha (instead of re-fetching live HEAD and blind-overwriting), so a concurrent push from another machine returns **409**, surfaced as a `github-conflict` error. The editors (`useTopicContentLifecycle.jsx`, `scheduleEditor.jsx`) then prompt the user to reload the latest rather than silently clobbering newer content (the pre-fix bug: a stale session overwrote a newer commit). After a successful commit the editor advances its base sha to `gitBlobSha(committedContent)` (`src/utils/gitBlobSha.js`, matches GitHub's blob sha) so consecutive saves don't false-conflict. `getGitHubFileAtHead` falls back to `download_url` when the Contents API omits inline content (files >1MB). `baseSha` is **opt-in**: omit it (course.json, schedule create/copy, add-topic) for the legacy fetch-live-HEAD behavior.
- **Shared UI primitives / design system.** Common form and dialog chrome lives in `src/components/ui/` — `Button`, `Input`, `Textarea`, `Select`, and `Modal` (a `<dialog>` shell), all composing their Tailwind classes from `src/components/ui/styles.js`, the single source of truth for radius, border, focus ring, disabled state, button variants (`primary|secondary|outline|danger|ghost`) and sizes (`xs|sm|md`); `styles.js` is unit-tested in `styles.test.js`. Build chrome from these primitives rather than re-deriving raw classes. The accent/signifier colour is **blue**; amber is reserved for semantic uses only (the AI "Discuss" button, the exam/DRA-final/interview-final assessment theme, warnings/banners, data-viz, and categorical colour arrays). Native `window.confirm`/`window.prompt`/`alert()` are **not used**: the app-wide `AlertProvider` (`src/contexts/AlertContext.jsx`, mounted in `index.jsx`) exposes `useAlert()` → `showAlert({message,type})`, `showConfirm(options) → Promise<boolean>`, and `showPrompt(options) → Promise<string|null>`, all rendered with the `Modal`/`Button`/`Input` primitives (`options` may be a message string or `{ message, title, confirmButtonText, cancelButtonText, danger, placeholder, initialValue }`). They are named `show*` (not `confirm`/`prompt`) deliberately, so a consumer can never shadow the `window.confirm`/`window.prompt` globals and silently fall back to a native dialog. The ref-driven dialog helpers `hooks/confirmDialog.jsx` and `hooks/inputDialog.jsx` also wrap `Modal`. **Tabs** are one component (`src/components/Tabs.jsx`): `variant="fill"` for equal-width tab bars (sidebar, discussion panel), `variant="scroll"` for content-width scrollable tabs (assessment workspaces) — there is no separate `TabBar`.
- **Markdown rendering & styling.** Topic prose is styled by a self-contained, token-based `src/components/markdown.css` (`--md-*` tokens for color/elevation/tables/etc.); `github-markdown-css` was removed. Dark mode re-points those tokens in `src/dark.css` (keep the two in sync when adding a token). Mermaid SVGs use a fixed white canvas in both themes so transparent regions do not inherit the page background. `Markdown.jsx` is the live renderer and `MarkdownStatic.jsx` the static/export one. `MarkdownInstruction` caps normal topics to a centered `max-w` reading column but renders **schedule** topics full-width with a locked (sticky) header row — schedule tables carry the `markdown-table-scroll--sticky-head` wrapper, whose styles live in `markdown.css`.
- **Single source of truth for derived metrics.** Mastery/time/completion are derived from the enrollment's progress blob by **`src/utils/progressSummary.js` (`deriveProgressSummary`)** — on the client, which has the course structure. Do **not** add a second implementation (e.g., server-side) that can drift; that drift was a real bug. If the server must restrict data, do it on stable columns (e.g., `enrollment.createdAt`), not on recomputed values.
- **Client-side observability** (operational telemetry, distinct from learner progress tracking in the `progress` table) lives entirely in **`src/observability/observability.js`** and has **two independent, config-gated sinks**, split along the metrics-vs-logs line:
  - **Logs → Grafana Loki** via our own **buffered pusher** (no SDK). Entries — our action events (`enroll`/`unenroll`/`login`; topic views & interaction submits are **not** logged — that audit trail already lives in the Supabase `progress` table, and their engagement is in metrics), instrumented call failures (`<op>_error`), and uncaught JS errors / unhandled rejections (captured via `window` `error`/`unhandledrejection` hooks) — accumulate in a bounded in-memory buffer and flush **batched** (timer `LOG_FLUSH_INTERVAL_MS`, a `LOG_BATCH_MAX` size trigger, and `pagehide`), never one POST per event. Each is a JSON line (`event_name` + user id/role + id-based attrs like `courseId`/`topicId`) tagged `info`/`error`. Course/topic **titles are not in the logs** — per-course/per-topic engagement lives in metrics (below), so Loki volume stays lean at scale. The one deliberate PII field is the attempted `email` on a `login` **failure** event (for support/typo/abuse triage); successes carry `user_id`/`role` instead. The browser POSTs the batch (with the public anon key) to the **`logpush` edge function** (`install/supabase/functions/logpush/`), which groups entries into Loki streams (`{app:"masteryls", level}`, low-cardinality labels; detail in the JSON line) via `buildLokiStreams` and pushes to Loki (`LOKI_URL`/`LOKI_AUTH` from its env). Query with `{app="masteryls"} | json | event_name="…"`. No source-mapped stacks (we don't upload source maps) and no web-vitals — intentional tradeoffs for owning the pipeline; Faro was removed.
  - **Metrics → Grafana Mimir** via **server-side aggregation** (no SDK dependency, Grafana token never in the client, and the OTLP gateway has no browser CORS anyway). Pipeline: the browser accumulates **deltas** in memory — a `masteryls_client_call_duration_ms{op,status}` histogram (`op` = `edge:<fn>`|`github`, `status` = `ok`|`4xx`|`5xx`|`error`) plus generic counters: `masteryls_client_login_total{result}`, and **engagement** `masteryls_client_topic_views_total{course,topic}` / `masteryls_client_interactions_total{course,topic}` / `masteryls_client_enrollments_total{course}` labelled by course/topic **name** (so engagement queries need no logs; titles stay out of Loki). It POSTs a compact JSON delta (`{ calls, counters }`, built by `buildDeltaPayload`; counters come from `recordTopicView`/`recordInteraction`/`recordEnrollment`/`recordLogin`) with the public anon key to the **`telemetry` edge function** → which allowlists counter metric names + label keys and calls the `record_client_metrics(calls, counters)` RPC to atomically fold the deltas into the **`client_metric`** table (cumulative running totals, keyed by `metric`+`labels`jsonb, RLS-locked to the service role; the RPC caps distinct series per metric via `max_series_per_metric` so free-form course/topic labels can't explode cardinality) → the scheduled **`telemetryflush`** edge function (pg_cron, ~1/min) reads that table, builds **one cumulative OTLP payload** (`buildOtlp`, `aggregationTemporality: 2` — Mimir rejects delta), and pushes it to Grafana (`GRAFANA_OTLP_URL`/`GRAFANA_OTLP_AUTH` from its env). Because the server is the **single writer**, metrics carry only aggregate labels — **no per-session/instance id** — so cardinality is fixed regardless of how many browsers are online. The latency bucket bounds are duplicated in the client (`LATENCY_BUCKETS_MS`) and `telemetryflush/handler.js` and **must stay in sync** (client sends bucket counts positionally). `buildDeltaPayload`, `buildOtlp`, and `httpClass` are pure/unit-tested. Query with `sum(rate(…_count[5m]))` / `histogram_quantile(.99, sum by (le)(rate(…_bucket[5m])))` — no `instance` to aggregate away.
  - Config: `config.observability = { enabled, appName, logs: { enabled }, metrics: { enabled } }`. `enabled` is the master switch; each sink activates when its own flag is true and Supabase config is present. **No Grafana credentials in the client** — they live **server-side** in the edge functions' env: `supabase secrets set LOKI_URL=… LOKI_AUTH='Basic …' GRAFANA_OTLP_URL=… GRAFANA_OTLP_AUTH='Basic …'`. Deploy all three observability functions (`logpush`, `telemetry`, `telemetryflush`) with `--no-verify-jwt`, and apply the `client_metric` table/RPC and pg_cron flush schedule in `schema.sql`. CI sets both flags true. A ready-to-import Grafana dashboard lives at `install/grafana/masteryls-client-dashboard.json`.
  - Exports: `initObservability(user)` (bootstrapped once in `index.jsx` after the user resolves), `setObservabilityUser(user)` (re-tagged on login/logout in `app.jsx`; non-PII — only `user.id` + coarse role root/editor/mentor/learner), `logAction(name, attrs)`, `recordLogin(result)`, `httpClass`/`serializeMetrics` (pure), and **`instrument(op, ctx, fn, classify?)`** — the key helper that times an async op, records latency+status into the histogram, and on failure emits an error log event, all **without altering the result or swallowing the rejection**. **Every runtime export is a safe no-op until its sink is initialized**, so the disabled (default) build is behaviorally unchanged — the regression gate.
  - Choke points: all Supabase edge calls funnel through the private `service.invokeEdge()` (op `edge:<fn>`; in-band non-2xx errors are reclassified to 4xx/5xx via the Response status while the `{data,error}` shape is preserved), `makeGitHubApiRequest` is `instrument`ed (op `github`, status from `response.status`), `verifyOtp` records login success (with the user) and `login.jsx`'s catch records login failure (with the attempted email, covering both `requestOtp` and `verifyOtp` failures), `logAction` marks enroll/unenroll (`service`), and topic-view/interaction-submit are **metrics-only** (`recordTopicView`/`recordInteraction` in `useCourseOperations.addProgress`), not logged. Lean by design — **no distributed tracing** and no Faro SDK; add new instrumentation through these helpers rather than introducing an SDK import.

## Data model essentials (gotchas)
- **Pulse due dates** use the course calendar timezone (`America/Denver`) when interpreting Canvas timestamps. Learner pulses use Canvas `effective_due_dates` keyed by the exact learner's Canvas user ID as the date of record; they do not assume a due date embedded in a submission belongs to that learner. Course-wide base dates provide context for extensions, which are mentioned only when the learner's effective date is later. Course and section pulses use the course-wide base date. The `canvasgradebook` Edge Function and client must be deployed together for learner-specific due dates.

- **Course Pulse / Section Pulse / Learner Pulse History** are term-scoped archived Markdown snapshots shown in MasteryView. Each pulse is one `public.pulse` row (no stored sequence number); the "Pulse N" label is **derived from creation order at read time** in `service.getPulses` (newest-first, so the oldest is Pulse 1), and edits update its Markdown in place. RLS lets any course overseer (root/editor/**mentor**) read all pulses, course/section included; only root/editors generate or edit course/section pulses (the roster **Pulses** tab shows mentors the archive read-only — no Take-pulse/Edit). Mentors can also create learner-target pulses in courses they oversee; learners can create/read only learner pulses tied to their own enrollment. Course/section pulses may name learners, so they stay overseer-only and are never learner-visible. The course/section archive is on the roster MasteryView's **Pulses** tab (`canViewPulses` = overseer to show it, `canManagePulses` = root/editor for the generate/edit controls); learner pulse history is on the learner detail's **Pulses** tab. A learner's **own latest pulse is also surfaced on their dashboard card** (`src/views/dashboard/courseCard.jsx`): when a pulse exists it replaces the course blurb with a body-only plain-text excerpt (`pulseSummaryText` in `src/utils/pulseMarkdown.js`, which drops heading lines so the title isn't shown), labeled by a **"Latest pulse"** link to `course/:courseId/mastery?tab=pulses`, which `learnerMasteryView.jsx` reads (`useSearchParams`) to open the Pulses tab. `dashboardView.jsx` loads the latest learner pulse per enrollment in one query via `service.getLatestLearnerPulses(enrollmentIds)` (newest-first, deduped by `enrollmentId`; RLS limits rows to the learner's own); failures fall back to the description. The card keeps its whole-card link into the course via a stretched-link (`after:inset-0`), with the pulse link layered above it. A **learner** pulse view (the learner's own, or an observer's drill-down) is **locked to the learner's enrollment term** — resolved from their section via `resolveLearnerPulseTermId` (`src/utils/pulseTerm.js`) — and shows that term as a static label with **no term chooser**; course/section pulse views keep the term chooser. When the enrollment has no term (schedule-less/legacy course, or no section), the learner pulse view shows **nothing** (no term, controls, or history). A **self-pulse reminder** nudges a learner to take their own pulse: `usePulsePromptReminder` (`src/hooks/usePulsePromptReminder.jsx`) shows a slim dismissible banner (`PulseReminderBanner`) atop the classroom when the viewer is the enrolled learner (not an overseer/observer), **today is within the learner's dated schedule window** (`isWithinScheduleWindow` in `src/utils/pulsePromptSchedule.js` — undated/no-section → no reminder), reminders aren't opted out, and `shouldPromptForPulse` passes (last pulse ≥7 days old, not prompted in 24h). "Last pulse" comes from `service.getLatestLearnerPulses`; the 7-day/24-hour throttle is tracked per course inside the local `uiSettings-<courseId>` blob (a `pulsePrompt` sub-object, via `readPulsePromptState`/`writePulsePromptState` → `service.get/saveEnrollmentUiSettings`), so it never bleeds across courses. The banner's only actions are **Take pulse** and dismiss (snooze for the 24h window). **Take pulse** navigates to `…/mastery?tab=pulses&take=1`; the `take=1` one-shot makes `PulseArchive` auto-start the pulse **on the pulse page** (after the term resolves, param cleared first so a refresh won't regenerate) — generating in the classroom and navigating would abort the in-flight request, so it kicks off after navigation instead. Opting out lives in one place: a **"Remind me to take my pulse"** checkbox in the learner's own Pulse History header (`PulseArchive`, shown only when `user.id === targetId` and the viewer is not an overseer), which writes `enrollment.settings.pulsePromptsDisabled` (DB, via `service.setEnrollmentSettings` / `courseOps.setEnrollmentPulsePromptsDisabled`; RLS "User manage self" allows it — no schema change). Default is reminders on. During generation, the archive shows an animated, accessible status with changing stage descriptions for evidence collection, generation, saving, and history refresh (the user-facing messages deliberately do not mention AI); it deliberately provides no percentage or time estimate. Learner analysis pulses and learner-directed feedback pulses share `collectLearnerAnalysisEvidence` in `useCourseOperations.jsx`, which gathers Canvas grades, assigned schedule/deadlines, progress activity, section attendance/check-in responses, and a few essay examples with evaluator feedback. Course/section pulses use `collectCourseSectionPulseEvidence`: term-bounded progress is summarized in Postgres by `pulse_progress_evidence` and returns counts plus bounded recent-event/essay examples (never the full event history to the browser); attendance RPCs are called once per attendance-enabled section; schedule content is read once per assigned schedule; Canvas grades use one `canvasgradebook` roster request that fetches paginated users, enrollments, and assignments, then submissions only for assignments due in the selected term. The Edge Function requests Canvas assignment `all_dates` with `override_assignment_dates=false`, uses the base (course-wide) due date for term filtering and summaries, and still aggregates each learner’s submission/grade despite a personal override. Schedule display dates are parsed into ISO calendar dates before term filtering; the schedule is authoritative for course due dates, while Canvas due timestamps remain gradebook metadata and mismatches are surfaced. This avoids per-learner Canvas calls and avoids fetching every course submission when only a term is being reported. The client aggregates matched Canvas data by roster section; current course grade is distinguished from assignments due in the selected term. **Milestone completion is Canvas-authoritative when the course is Canvas-linked.** Each schedule deadline carries a `completionSource`: `reconcileScheduleDeadlinesWithCanvas` (`src/utils/pulseEvidence.js`) matches a milestone to its Canvas assignment (accent/punctuation-insensitive) and sets `completionSource: 'canvas'` with a `canvas` block (`completed`/`notCompleted`/`graded`/`missing`/`late`/`averagePercent`); otherwise it stays `completionSource: 'in-app'`. Canvas **completed** means the learner earned a passing grade (any score greater than zero) or is excused — computed as `completedCount` in `summarizeCanvasRosterGrades`. It is grade-based, so a zero, a `missing` zero, and an ungraded assignment are all **not** completed. This deliberately is not `submittedAt` (many projects are pass-off-graded with no submission timestamp), not `gradedCount` (a zero is a grade but not completion), and not the inverse of `missing` (Canvas only flags work missing after its due date, so a not-yet-due milestone must not read as fully completed). The milestone's MasteryLS-derived counts are relabeled `inAppCompleted`/`inAppIncomplete`/`inAppStatusUnavailableFor`: they are the authoritative completion only when `completionSource` is `in-app` (course not linked to Canvas, or no matching assignment), and are a MasteryLS-only subset — never the milestone completion — when it is `canvas`. The prompt enforces this. These pulses also include roster-wide mastery/completion/time rollups and bounded focus/event examples. Course-scoped editors and mentors are excluded from the learner roster, event/essay RPC summaries, attendance rollups, schedule completion counts, Canvas grades, and focus examples; learner-target pulses are unchanged. The `pulse_progress_evidence` RPC and optional `attendance_sessions(..., p_exclude_course_staff)` argument are defined in `install/supabase/schema.sql`; applying schema changes to the database is a separate deployment step. **Progress is reported as topic mastery (percent) only** — completed-topic counts were dropped as redundant. **The mastery-trend chart is built programmatically, not by the model:** the prompt forbids the model from authoring any diagram and has it emit a `{{MASTERY_TREND_CHART}}` placeholder after the Status indicators table; `buildMasteryTrendChart`/`insertMasteryTrendChart` (`src/utils/pulseMasteryChart.js`) then plot **every** available snapshot (so the chart grows over time instead of the model's usual two points). Trend data is read from a machine-written **metrics marker** appended to each pulse — `buildPulseMetricsMarker` writes `<!-- pulse-metrics: date=… mastery=… canvas=… -->`, and `extractPulseTrendPoint` reads it (falling back to parsing the status table for legacy pulses); this fixed learner charts never growing, because the old table parser required an "avg" label learner tables don't have. `buildPulseTrendHistory` returns up to eight chronological snapshots; course/section history accepts only pulses with the `course-students-no-staff-v1` cohort marker. The pulse prompt (`buildPulsePrompt` in `src/utils/pulsePrompt.js`) sets the voice by target: **learner** pulses are written in the **second person** (a mentor speaking to "you"), while **course/section** pulses stay **third person** for overseers and may name learners. The generated Markdown begins with a short **lead summary** paragraph (≤180 chars, no heading) above `## Overview`, carries an **`## Ongoing threads`** section before `## Evidence notes`, and has **no top-level title heading and no snapshot-date line** (removed to keep pulses compact; trend extraction falls back to `pulse.createdAt`). **`## Ongoing threads` is a carried-forward running ledger** of multi-pulse objectives/issues: each pulse starts from the previous pulse's Ongoing threads (the full prior pulse is in the prompt) and updates each entry's status (new/continuing/improving/escalating/resolved) — celebrating long-running problems that finally resolve and flagging ones neglected across many pulses — while the body sections (Overview, Change-since, Positive signals, Needs attention, Priorities) focus on what changed **since the last pulse**. This self-accumulates via carry-forward (no schema change). The dashboard card excerpt (`pulseSummaryText`) prefers that lead summary, falling back to the Overview body, then any prose. Edits use `MarkdownEditor` with its authoring toolbar hidden, alongside a live `Markdown` preview in a draggable split pane; pulse saves do not write course Markdown to GitHub.

- **`enrollment.progress` is a cached JSON rollup**, not the source of truth for history. It can be stale (mastery was intentionally moved to runtime derivation to avoid a write race). The **`progress` table is an append-only event log** — every attempt/action is its own row with `createdAt` and `details`. "First attempt vs latest attempt" summaries read the full `progress` history.
- **Terms, Schedules, and Sections** (course-scoped DB tables: `term`, `schedule`, `section`). A **term** is a period of instruction (semester/quarter/short block); a **schedule** is the content/delivery calendar whose Markdown content stays in GitHub at `schedule.contentPath` (the DB row is metadata); a **section** ties a roster to one schedule within a term (a schedule may back many sections). Each **`enrollment.sectionId`** (nullable) locks a learner to one section → one schedule. Schedule resolution is **section-derived** via `src/utils/scheduleResolution.js` (`resolveLearnerSchedule`): `getScheduleFiles`/`getScheduleTopic`/`getLockedScheduleFileId` (in `useCourseOperations.jsx`) build descriptors from the **DB `course.schedules`** rows (by `contentPath`, descriptor id = schedule id) when present, falling back to the legacy GitHub `course.json` `schedule.files` (descriptor id = file id) / `enrollment.settings.selectedScheduleFile` when there are no DB schedule rows (schedule-less or not-yet-migrated courses). A learner sees only their section's schedule (picker hidden/locked); overseers keep the full picker, except when **observing** a learner (they then see that learner's locked schedule). Sections/schedules are loaded in `getCourse` (`useCourseOperations.jsx`) and attached as `course.sections`/`course.schedules`; the newer Terms & Sections flow uses DB rows, while the legacy schedule creation/editor path can still read and write `course.json` schedule data when no DB schedule rows exist. Existing enrollments were migrated to sections by a one-time backfill (built from each course's legacy `course.json` schedule files, keyed on `schedule.legacyFileId`, setting `enrollment.sectionId` only when null); that migration is complete and its script/helper have been removed. `term`/`schedule`/`section` are publicly readable; writes are root/editor (`auth_manages_course`). Editors/mentors remain **course-scoped** (no section-scoped permissions). At enrollment, `service.createEnrollment` auto-assigns the sole section when a course has exactly one; when a course has **multiple** sections the dashboard self-enroll shows a **section picker** (`dashboardView.jsx`) and passes the chosen `sectionId`. The picker offers only sections whose schedule's date range includes today (`src/utils/sectionEnrollment.js` `enrollableSections`); a section with no schedule or an undated schedule is always offered, and a course whose sections are all outside their schedule date ranges shows a "no open sections" message. Editors manage **terms** and **sections** in the **Terms & Sections view** (`src/views/sectionsAdmin/sectionsAdminView.jsx`), which renders **in the classroom content pane** as a synthetic `sections` topic (`courseOps.getSectionsTopic`, editor/root only — learners never see it) so it reads as part of the course rather than a separate screen. It is reached from the course **TOC** entry (`contents.jsx`, alongside Schedule/Attendance), which routes to `course/:courseId/sections`; `ClassroomPage` resolves the route like the schedule/attendance routes without persisting it as the landing topic. The classroom owns the app bar (course title + the topic title "Terms & Sections"), so the view no longer sets it itself. Sections are shown nested under their term, so a section's term is conveyed by its grouping, not a per-row dropdown; adding uses distinct highlighted forms. CRUD via `service` `createTerm`/`updateTerm`/`createSection`/`updateSection`/`setEnrollmentSection`. **Deletion** (`service.deleteSection`/`deleteTerm`, gated in the UI, never for items with learners): a section shows trash only when it has **0 learners and is not the last section in its term** (a term always keeps ≥1 section); a term's delete (trash) control stays visible but is **disabled while any of its sections has learners**, and when used removes the term and its sections (`section.termId` cascades) but **keeps its schedules** — `deleteTerm` first detaches them (`schedule.termId → null`) so the `schedule.termId` cascade does not drop them, since schedules are managed independently and may back sections in other terms. The same view lists schedules below terms with matching card formatting, and supports renaming, editing their date range (`service.updateScheduleRow`), **copying** a schedule (a dialog takes a title and an optional *first session date*; when set, `copyCourseSchedule` shifts every dated row via `remapScheduleToStartDate` so the first session lands on that date, keeping session spacing), **viewing** one (a View button that sets `selectedScheduleFile` via `saveEnrollmentUiSettings` and navigates to the classroom `…/schedule` route), **creating** a new one, and **deleting** one — `createCourseSchedule`/`copyCourseSchedule` (`useCourseOperations.jsx`) commit the markdown to GitHub and insert a DB `schedule` row with its `contentPath` (so brand-new schedules resolve natively, no `course.json` write), while `deleteCourseScheduleById` removes the backing GitHub file (`deleteGitHubFile`) and the row (`service.deleteScheduleRow`); each schedule shows its **section-usage count** and the delete control stays visible but is **disabled while any section references** that schedule (so no section is left schedule-less). A schedule's **title and date range are owned here (the DB row)**: the classroom **schedule editor** (`src/components/editor/scheduleEditor.jsx`) edits only the schedule *content* (weeks/sessions, external links, special days) — it has no title field, no "Dates covered" range, and **no Default/Delete/New-schedule controls** (creating, copying and deleting schedules all live in the Terms & Sections view); its chooser only switches among existing schedules. There is **no "default schedule" concept** — the DB `schedule` table has no default flag, and when no section lock and no saved selection apply the oldest schedule row is the implicit fallback (`getScheduleFiles`/`getSelectedScheduleFile`). The **schedule name is not stored in the markdown**: `serializeScheduleMarkdown` does not write a `# ` title heading, and the displayed name comes from the DB `schedule.title`. `parseScheduleMarkdown` still skips a leading `# ` heading so legacy content authored with one parses cleanly. Legacy schedule file metadata is retained during fallback compatibility; learner section assignment lives in MasteryView/cohorts and editor bulk add-learner workflows; the roster enrollment action lets root/editors move a learner to another section or unenroll them.
- **MasteryView renders in the classroom content pane** (like Schedule/Sections), not as a standalone screen. It is a synthetic `mastery` topic (`courseOps.getMasteryTopic` — an overseer gets the roster, an enrolled learner gets their own view) reached from the TOC affordance (`contents.jsx`) and the toolbar button (both go to `course/:courseId/mastery`); the per-learner drill-down is `course/:courseId/mastery/learner/:learnerId`. `ClassroomPage` resolves these routes like `/schedule`/`/sections` (not persisted as the landing topic), and `instruction.jsx`'s `mastery` case renders `components/instruction/masteryInstruction.jsx`, which dispatches the roster (`masteryView.jsx`) vs the per-learner view (`learnerMasteryView.jsx`). Both are embedded-only now — no course picker (the course is the classroom's); the old standalone `/masteryview` routes and the app-bar menu item were removed. **MasteryView roster** (`src/views/masteryView/`) fetches a _trimmed_ per-enrollment blob from the `masteryoverview` edge function and does **sorting, filtering, and pagination entirely client-side** (so display and ordering always share one computation path). A single-learner drill-down request returns the _full_ blob. The **Section** filter restricts the roster server-side by `enrollment.sectionId` (the `masteryoverview` edge function accepts an optional `sectionId`); The filter can be preselected with `?section=<sectionId>` when opening `course/:courseId/mastery`. "All sections" fetches the whole course. (A legacy `startDate`/`endDate` `enrollment.createdAt` window is still honored by the edge function for backward compatibility, but the UI now filters by section.) When attendance is enabled for the course, the roster requests `includeAttendance: true`; the edge function then counts each learner's type-`attendance` progress rows (`tallyAttendanceByLearner`) and returns `attendedCount` per row, which the table shows as a sortable **"Classes Attended"** column (raw attended count, no total — a course can span multiple sections). The field is omitted when not requested, so non-attendance courses pay no extra query. On the single-learner drill-down (`learnerMasteryView.jsx`), when the viewer is an overseer and the course is Canvas-linked (`course.externalRefs.canvasCourseId`), a **"Canvas grades"** link appears to that learner's Canvas grades page. Canvas's web route needs the learner's numeric Canvas user id, which isn't stored in MasteryLS — it's resolved on demand by the `canvasgradebook` edge function's `mode: 'userLookup'` (matching by email/login via `findCanvasLearner`), and the URL is built by `getCanvasGradesUrl` in `canvasSync.js`. `userLookup` is a read-only overseer action so it also admits mentors; grade submission stays root/editor/self. The learner detail has a full-width tab bar below the overview ordered Topic Activity, optional Attendance, Last Activity, Daily Activity, and optional Canvas; the Canvas tab appears only when linked and resolved; opening it lazy-loads the learner's current Canvas grades via the `canvasgradebook` `mode: 'grades'` (overall course grade + per-assignment breakdown, trimmed by `buildGradeSummary`; read-only, overseer-or-self, mentors included) and renders them with `canvasGradesPanel.jsx`.
- **Attendance is section-based.** It uses a dedicated `attendance` table (each session carries a `sectionId`) + Postgres **RPCs** (`open_attendance(catalogId, sectionId, questions)`, `close_attendance`, `record_attendance`, `attendance_sessions(catalogId, sectionId?)`) under RLS; a check-in writes a `progress` row of type `attendance` referencing the session, with the learner's answers in `details.answers` keyed by question id. Attendance is **enabled per section** via `section.attendanceEnabled` (the old course-level `course.settings.attendance` flag was removed); editors/root manage this setting in the Terms & Sections view (`sectionsAdminView.jsx`), while the attendance view lets them open sessions for enabled sections (`attendanceAdmin.jsx`). The attendance affordance is shown to a learner only when their section has attendance enabled (`getAttendanceTopic`/`courseHasAttendance` in `useCourseOperations.jsx`). At most one session may be open per section. Opening attendance picks a section; `attendance_sessions` scopes sessions and the `enrolledCount` denominator to a section when given one. Every session asks the standard wellness question (`DEFAULT_ATTENDANCE_QUESTION`, id `q1`, in `attendanceUtils.js`); `attendance_sessions` returns a per-session `answerTally` (`{ [questionId]: { [choice]: count } }`) so the charts can show the results. There are two attendance charts, named as siblings and sharing `BarChartSvg`, `attendanceUtils.js`, and the `SentimentLegend` swatch row (`sentimentLegend.jsx`): **`courseAttendanceChart.jsx`** (`CourseAttendanceChart`) stacks every session's answers as sentiment-coloured bars for the whole course (instructor Attendance page only — it is intentionally not duplicated in MasteryView); **`learnerAttendanceChart.jsx`** (`LearnerAttendanceChart`) draws only the classes one learner attended, each bar coloured by their answer (learner's own Attendance page + MasteryView learner drill-down). Now that attendance is section-based, passing the learner's `sectionId` scopes the sessions so the chart shows an honest **"attended N of M"** (M = that section's sessions); without a `sectionId` it falls back to the attended-only view (no total). The learner's own page threads `courseOps.getCurrentSectionId()`; the MasteryView drill-down does not yet pass a section (shows attended-only there for now). Sentiment colours/segment helpers live in `attendanceUtils.js`; handle legacy sessions/rows that predate the question (no answer → neutral "No response"). **Historical sessions** created before section-based attendance carry `sectionId = null`; a one-time backfill (since removed) attributed them to a section **only for single-section courses** (closed sessions), leaving 0-/multi-section courses' sessions null for manual handling — so a null `sectionId` remains a valid "unattributed legacy" state the charts/RPCs still handle.
- **MasteryView learner detail tabs.** The learner overview header remains above a full-width tab bar. The tabs are Topic Activity, optional Attendance, Last Activity, Daily Activity, Pulses, and optional Canvas, in that order; Topic Activity is the default when topic data exists and contains the instruction-topic summary table. Pulses contains the learner's term-scoped pulse archive. The learner email and header actions wrap on narrow screens. Daily Activity records and Canvas grades remain lazy-loaded when their tabs are first selected.
- **MasteryView learner feedback pulses.** Root users, editors, and mentors can generate learner-directed feedback from the learner detail **Pulses** tab. The action uses `generateLearnerFeedback` and shared `collectLearnerAnalysisEvidence`, then stores the generated title and Markdown message as a `pulse` row with `pulseType = feedback`; the learner can read it in their own pulse history. Feedback entries are marked with an amber **Feedback** chip — in the archive history list (after the "Pulse N" number) and on the learner's dashboard card (beside the "Latest pulse" label). There is no separate email dialog or roster/header Feedback action. Creating feedback pulses requires the `pulseType` column and learner-target overseer permissions in `install/supabase/schema.sql` (apply schema changes to the database as a separate deployment step). Learners retain the ability to take their own analysis pulses.
- **Course content** is not in the DB — it's Markdown pulled from GitHub. The `topic` table is only a full-text search index.

## Testing

Commands (see `package.json`):

- `npm run test:unit` — node unit tests (`src/**/*.test.js`), pure logic.
- `npm run test:edge-auth` — edge-function handler tests (`install/supabase/functions/**`).
- `npm test` — Playwright e2e (`tests/`). Needs the dev server/browsers; specs mock Supabase/GitHub via route interception (`tests/testInit`, `tests/fixtures`).
- `npm run build` — `vite build`; use it as an integration smoke check for client changes.

**Expected workflow (not optional):**

- While developing a feature, **run the tests relevant to what you're touching** (the unit/handler test for the logic, the matching Playwright spec for the UI) and keep them green as you go.
- On **completion of a feature, run the full suite** (`test:unit`, `test:edge-auth`, and the Playwright specs, plus `vite build`) before considering it done.
- **New features and bug fixes should add/adjust tests** that raise confidence and guard against regression. Edge-function logic → handler test; pure helpers → `*.test.js`; user-facing behavior → Playwright spec. When a fix is prompted by a bug, add the test that would have caught it.

## Deployment notes

- **Edge functions must be deployed** to take effect (they run on the hosted Supabase project, not from the local tree): `supabase functions deploy <name> --project-ref <ref>`. Changing a `handler.js` without deploying does nothing in production.
- **Schema changes** (`install/supabase/schema.sql`) — tables/indexes/RLS/RPCs — must be applied to the database separately.
- **Client/server contract changes ship together.** If an edge function's request/response shape changes, deploy it with the client release that depends on it; there is no backward-compat window unless you build one.
- The in-app **About page reads docs from GitHub `main` at runtime**, so doc/README path changes only take effect once merged to `main`, and relative image paths in a doc resolve relative to that doc's location in the repo.

## Working principles (how to make changes here)

- **Good design & patterns.** Favor clear, well-factored solutions over quick hacks. Respect the existing layering (UI → operations hook → service → Supabase) and the pure-handler/thin-wiring split for edge functions.
- **Modularity & clear organization.** Keep responsibilities separated; put pure logic in `utils/` (testable) and keep components focused. Reuse existing helpers (e.g., `deriveProgressSummary`, `scheduleMarkdown`) instead of re-implementing. Avoid duplicated computation paths that can drift.
- **Testing raises confidence.** Treat coverage as a feature: add tests that make new behavior safe to change and catch regressions. Run relevant tests during development and the full suite at feature completion (see Testing).
- **Suggest alternatives.** Don't just execute the literal request — when a cleaner design, a better-scaling approach, or a simpler path exists, surface it (with a recommendation) before or alongside doing the work. Flag tradeoffs the requester may not have considered.
- **Backward compatibility.** When changing existing code, data shapes, APIs, edge-function contracts, or the DB schema, consider existing data and callers. Prefer additive/compatible changes; when a breaking change is warranted, say so explicitly and coordinate the pieces (client + edge function + schema) that must change together.
- **Keep this file updated.** Reflect any architectural, data-model, workflow, feature, or layout change here as part of the same change.
- **Keep user documentation current.** For every code change, review the relevant documentation under `docs/` and update it in the same change whenever behavior, workflows, settings, or other documented details have changed. Treat stale user-facing documentation as unfinished work.
